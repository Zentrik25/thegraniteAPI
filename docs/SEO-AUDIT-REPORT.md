## Executive Summary

**Business Type:** Independent digital newsroom (Zimbabwe) — BBC-style national news platform.

**Top 5 Critical Issues:**
1. **RSS feed NOT purged on publish** — `purge_article_cache()` purges a dead URL (`/rss/latest/`) instead of `/feed.xml`, so Cloudflare never invalidates the feed after new articles are published.
2. **`/api/revalidate` webhook never includes `/feed.xml`** — Next.js Data Cache for the feed is not cleared on publish; feed data is up to 15 minutes stale.
3. **`/feed` returns 404** — The WordPress-convention URL (`/feed`) that most feed readers auto-discover is not redirected to `/feed.xml`.
4. **`purge_article_cache` also misses `/feed` URL** — Since `/feed` is the canonical URL users subscribe to in readers, its CDN cache (if it existed) would never be purged either.
5. **Homepage title duplicates brand name** — `"The Granite Post — Zimbabwe's Journal of Record — The Granite Post"` — Google may truncate or penalize keyword stuffing.

**Top 5 Quick Wins:**
1. Fix `cloudflare_purge.py` line 102: change `/rss/latest/` → `/feed.xml` (1-line fix, immediate impact).
2. Add `purge("/feed.xml")` to `revalidate/route.ts` (1-line fix).
3. Add a Next.js redirect: `/feed` → `/feed.xml` in `next.config.ts`.
4. Fix homepage title tag — remove duplicate brand name.
5. Add `mainEntityOfPage`, `articleSection`, and `keywords` to NewsArticle JSON-LD.

## 1. RSS Feed — Root Cause Analysis

### Why new articles don't appear in Inoreader and other feed readers

This is the primary support issue. There are **three compounding bugs** preventing timely feed updates:

---

### Bug 1 — Cloudflare purge targets a dead URL (CRITICAL)

**File:** `c:/dev/thegraniteAPI/core/cloudflare_purge.py`, line 102

```python
# CURRENT — WRONG
urls = [
    ...
    f"{site_url}/rss/latest/",   # ← This URL returns 404. Nothing is purged.
]
```

The actual RSS feed is served at `/feed.xml` (generated by the Next.js frontend). When an article is published, Django's `post_save` signal calls `purge_article_cache()`, which asks Cloudflare to purge `/rss/latest/`. That URL does not exist. Cloudflare silently ignores 404 URLs in purge requests, so `/feed.xml` remains cached at the CDN edge for `max-age=900` (15 minutes) after every publish event.

**Fix — `cloudflare_purge.py`:**
```python
urls = [
    f"{site_url}/articles/{slug}/",
    f"{site_url}/api/v1/articles/{slug}/",
    f"{site_url}/api/v1/articles/",
    f"{site_url}/api/v1/articles/top-stories/",
    f"{site_url}/api/v1/articles/breaking/",
    f"{site_url}/sitemap.xml",
    f"{site_url}/news-sitemap.xml",
    f"{site_url}/feed.xml",   # ← ADD THIS (was "/rss/latest/" — wrong URL)
    f"{site_url}/feed",       # ← ADD THIS for readers subscribed to /feed
]
```

---

### Bug 2 — Next.js Data Cache not purged on publish (HIGH)

**File:** `c:/dev/thegraniteFRONTEND/src/app/feed.xml/route.ts`, line 51

```typescript
const res = await fetch(
  `${API_BASE_URL}/api/v1/articles/?page_size=20&ordering=-published_at`,
  { next: { revalidate: 900 } }  // ← Data Cache holds stale results for 15 min
);
```

**File:** `c:/dev/thegraniteFRONTEND/src/app/api/revalidate/route.ts`

```typescript
purge("/");
purge("/search");
purge(`/articles/${article_slug}`);
// ← /feed.xml is NEVER purged here
```

The Django backend does not call `/api/revalidate` at all (it only calls Cloudflare's purge API). Even if it did, `/feed.xml` is missing from the revalidation list. Combined with Bug 1, the result is:

- Cloudflare serves stale `/feed.xml` from CDN for up to 15 minutes
- Next.js serves stale API fetch results for up to 15 minutes
- **Worst case: a new article takes ~15–30 minutes to appear in feed readers**

**Fix — `revalidate/route.ts`:** Add `/feed.xml` and `/news-sitemap.xml` to the purge list:

```typescript
purge("/feed.xml");
purge("/news-sitemap.xml");
```

**Fix — Django signals (`articles/signals.py`):** After calling `purge_article_cache`, also call the Next.js revalidate webhook:

```python
@receiver(post_save, sender="articles.Article")
def revalidate_nextjs_on_publish(sender, instance, **kwargs) -> None:
    if instance.status != "published":
        return
    try:
        import requests as http_lib
        from django.conf import settings
        secret = getattr(settings, "NEXTJS_REVALIDATE_SECRET", "")
        nextjs_url = getattr(settings, "NEXTJS_URL", "")
        if not nextjs_url:
            return
        http_lib.post(
            f"{nextjs_url}/api/revalidate",
            json={
                "secret": secret,
                "article_slug": instance.slug,
                "section_slug": getattr(instance.section, "slug", None),
                "category_slug": getattr(instance.category, "slug", None),
            },
            timeout=5,
        )
    except Exception as exc:
        logger.warning("Next.js revalidate failed for slug=%s: %s", instance.slug, exc)
```

### Bug 3 — `/feed` returns 404 (HIGH)

**Observed:** `GET https://www.thegranite.co.zw/feed` → 404

Most feed reader apps and browsers use one of these auto-discovery URLs by default:
- `/feed` — WordPress standard (most common)
- `/rss` — Legacy convention
- `/rss.xml` — Variant

The Granite Post's actual feed is at `/feed.xml`. If a user or app subscribed to `/feed`, they receive a persistent 404 and will never see any articles — new or old.

**Fix — `next.config.ts`:** Add a permanent redirect:

```typescript
async redirects() {
  return [
    { source: '/feed',    destination: '/feed.xml', permanent: true },
    { source: '/rss',     destination: '/feed.xml', permanent: true },
    { source: '/rss.xml', destination: '/feed.xml', permanent: true },
  ];
},
```

### Additional Feed Issues

**Feed item count is capped at 20** (`page_size=20` in the fetch). The Django backend supports 50 items (`[:50]`). Increasing to 50 gives readers more history, reducing the risk of missing articles published during long polling gaps.

**`news-sitemap.xml` also needs purging on publish.** Currently not purged by Cloudflare or Next.js revalidate. Google News discovery depends on the news sitemap being fresh.
